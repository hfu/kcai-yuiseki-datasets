# 東北6県の森林資源メッシュ・現存植生図の範囲読み（terrio-js、2026-10-31）

環境: Claude Code クラウドセッション、npm の terrio-js 0.4.2（Node 22）。配信は Hugging Face の `resolve/main/…`（CDN に転送）。`openUrl` のあと `read({bbox})`、`stats()` の受信量と要求数、`info()` の行グループ。

## 窓の決め方

- 各ファイルの `geo` メタデータの bbox（ファイルの座標系）の中心に、窓を置いた。
- 森林資源メッシュ: 各県のシートから約6枚おきに3枚（計18シート）。窓は中心の 2km 四方と 500m 四方（投影座標のメートル。bbox は幾何の座標系で与える）。
- 現存植生図: 県ごとの1ファイルの中心に、0.03°（約3km）四方と 0.2°（約20km）四方（植生図の幾何は EPSG:6668 の経緯度）。
- 計48回の読み。エラーは0。

## 結果

### 現存植生図（1ファイル・1行グループ・covering あり）

| 県 | ファイル | 0.03° の窓 | 0.2° の窓 | 受信量 |
|---|---|---|---|---|
| 秋田 | 234.9MB | 94 | 4,895 | どちらも全量（234.9MB） |
| 青森 | 139.7MB | 0 | 1,882 | 全量 |
| 福島 | 322.9MB | 152 | 4,875 | 全量 |
| 岩手 | 204.2MB | 97 | 3,931 | 全量 |
| 宮城 | 129.2MB | 122 | 8,196 | 全量 |
| 山形 | 162.2MB | 76 | 5,407 | 全量 |

- 窓の中のポリゴンが0件でも（青森の 0.03°）全量だった。所要時間は約2.5〜7.6秒（回線による）。
- `info()` では行グループの bbox が見える（`covering` が効いている）が、行グループが1つしか無いため、飛ばせない。

### 森林資源メッシュ（シートごとのファイル・1行グループ・covering あり）

- 36回のうち、地物がある窓では、受信量はそのシートのファイルの**全量**だった（0.10〜7.57MB）。2km の窓の地物数は最大10,404（20m セルの 102×102）。
- 地物が0件だった窓は8回。うち4回は、ファイルの 5〜18% で済んだ（秋田 10JE3 500m: 155KB／876KB、青森 10FD4: 215KB／2.57MB、岩手 10IE4 500m: 133KB／2.43MB）。残りの4回は小さなファイル（0.1〜0.2MB）を全量読んだ。
- 要求数は2〜5回。

## 読み取れること

1. **メッシュは分割（シート）のおかげで実用的に小さい。** 1つの窓は1〜数枚のシート（各8MB以下）で済み、県全体（約180〜340MB）を読む必要はない。窓がシートの境をまたぐと、またぐ枚数だけ読む。
2. **植生図は、窓が小さくても県の1ファイル（129〜323MB）を全量読む。** `covering` があっても、行グループが1つでは効かない（前の実験の estat-boundary-2020 と同じ。複数の行グループに分け、空間順に並べると、小さな窓の転送量が元の約9〜19%まで下がった）。
3. 地物が0件の窓では、同じ行グループの中でも一部しか読まないことがあった（メッシュの 5〜18%）。bbox の列を先に読んで判定している可能性があるが、仕組みは確認していない。

## 限界

- 窓は各ファイルの中心の2つのみ。シートの縁や、窓がまたぐ場合の枚数は測っていない。
- 配信は Hugging Face の CDN。時間は回線による。
- terrio-js 0.4.2 のみ。DuckDB、terrio CLI は未測定。
- 植生図を複数の行グループに書き直した場合の効果は、この6県では試していない（estat-boundary-2020 の実験からの類推）。
